## 一、系统总览

### 1.1 一句话概括

**飞书（人说话）→ 飞书桥 → 中继 → Copilot（AI 干活）→ HTTP MCP → 中继 → Kanzi Studio（执行）**

## 二、端到端数据流

### 2.1 场景 A：用户在飞书里说「把标题改成红色」

```
 1. 用户 → 飞书 App
    「把标题改成红色」

 2. 飞书服务器 → feishu_bridge（webhook 回调）
    桥认出是哪个 bot 的消息

 3. 桥 → relay 的 nlp_client 槽
    ws://10.10.118.152:58080/suijichao   （通道名 = bot 名）
    {role: "nlp_client", ...}

 4. relay 转发 → 同通道的 nlp_worker 槽
    （Copilot 正连在这个槽上）

 5. Copilot（AI）理解意图 → 决定调用 MCP 工具
    它连的是 kz_mcp_http 的 HTTP MCP 端点

 6. Copilot → kz_mcp_http：POST /mcp
    JSON-RPC: tools/call  name="kz_invoke"
    arguments: {target, method, args}

 7. kz_mcp_http 鉴权（X-Kanzi-User 请求头 + users.json 白名单）
    通过 → 转发到 relay 的 client 槽
    ws://10.10.118.152:58080/suijichao   {role: "client"}

 8. relay 转发 → 同通道的 server 槽
    （Kanzi Studio 插件正连在这个槽上）

 9. Kanzi 插件收到 JSON-RPC
    → 纯反射调用 Kanzi Studio API
    → 属性真的改了

10. 结果原路返回：Kanzi → relay(server) → relay(client, 定向回传)
    → kz_mcp_http → Copilot → relay(nlp_worker) → relay(nlp_client)
    → feishu_bridge → 飞书 → 用户看到「改好了」
```

### 2.2 场景 B：Kanzi Studio 插件里直接说自然语言

**前 3 步不同**，后面完全一样：

```
 1. 用户在 Kanzi Studio 聊天插件窗口输入
 2. 插件 → relay 的 nlp_client 槽（同一个通道）
 3. 之后走 4~10，与场景 A 完全相同
```

这就是为什么通道设计成 **nlp_client ↔ nlp_worker** 双向转发：
**飞书和 Kanzi 聊天插件是同一个入口的两种前端。**

### 2.3 场景 C：大批量结果外置

Kanzi 返回的数据太大（比如截图 base64、991 行本地化表）时：

```
Copilot ← kz_mcp_http
          「返回内容超过阈值（50 条 / 4096 字节）
           → 落盘到 tmp_results/ → 只回一个 URL」

Copilot 拿 URL 自己去取（用普通 HTTP 下载）
URL 主机 = result_public_host（必须 AI 可达，不能是 0.0.0.0）
```

**目的**：避免超长内容把 AI 上下文撑爆。

### 2.4 场景 D：飞书发图片/文件

```
飞书 → 桥的 inbox_<bot名>/ 目录（下载文件）
桥 → 桥自己的文件服务（http://<绑定IP>:8081/<bot名>/xxx）
Copilot ← 得到文件 URL → 自己去取
```

`inbox_<bot名>/` 由**自动清理**定期清理（默认超过 7 天、或超过 500 个文件时删最旧）。

## 三、核心组件详解

### 3.1 relay_multi（中继）—— 系统的中枢

**作用**：把「谁发的消息」转给「谁该收消息」。

**关键设计：按 URL 路径分通道。**

```
ws://10.10.118.152:58080/suijichao      → 通道 suijichao
ws://10.10.118.152:58080/zhenghaitao    → 通道 zhenghaitao
```

**通道名 = 用户名 = 飞书 bot 名。三者必须一致**，否则消息进不了同一个通道。

**每个通道 4 个槽：**

| 槽位 | 谁连 | 说明 |
|---|---|---|
| `server` | Kanzi Studio 插件 | 一台 Kanzi 一个 |
| `client` | kz_mcp_http | **可多连接并存**，支持定向回传 |
| `nlp_client` | 飞书桥 / 聊天插件 | 同通道只允许 1 个（新连接踢旧的） |
| `nlp_worker` | Copilot | AI 执行端 |

**两组双向转发：**

```
nlp_client  ←→  nlp_worker     （用户输入 ↔ AI）
server      ←→  client         （Kanzi ↔ MCP 客户端）
```

**为什么 Kanzi 不在线也不拒绝连接？**

历史版本在 Kanzi 没启动时用 `4001` 拒连。现在改为**连接保持 + 生成错误回包** ——
这样 Copilot 不会因为「Kanzi 还没开」而整个会话崩掉，只会收到一条「Kanzi 未连接」的错误。

**命令**：

```bash
relay_multi.exe --log-path logs/relay.log [--port 58080] [--host 0.0.0.0]
```

**日志降噪**：`websockets` 库的 INFO 日志压到 WARNING
（`connection open` / `connection close` 不再刷屏，**真错误仍然可见**）。

---

### 3.2 kz_mcp_http（MCP over HTTP）—— AI 的入口

**作用**：给 Copilot 提供一个标准的 **streamable HTTP MCP 端点**，
再把请求桥接到 relay → Kanzi。

**它不是 WebSocket 服务**（重要）：

```python
# kz_mcp_http.py
self.server = await asyncio.start_server(self._handle_conn, self.host, self.port)
```

是**裸 TCP/HTTP server**。所以健康检查必须用 **HTTP 探测**，
对它发 WebSocket 握手会失败。← 这是 v10→v11 的实测教训。

**鉴权**：

```
请求头 X-Kanzi-User: <用户名>
   ↓
查 users.json 白名单
   ↓
不在名单 / 没有头 → 403
```

**每个用户一条到 relay 的 client 槽连接。**

**白名单热更新**：改 `users.json` **不用重启**。

> 🔴 **白名单为空时组件直接 `sys.exit(1)`** —— 这是硬性要求，不是警告。

**外置结果**：超阈值内容落盘 `tmp_results/`，只回 URL（见场景 C）。

**命令**：

```bash
kz_mcp_http.exe --config conf/config.json --log-path logs/http.log
```

关键配置（由部署器生成）：

```jsonc
{
  "listen": "0.0.0.0:9001",                         // 必须 0.0.0.0 才能远程连
  "relay_base": "ws://10.10.118.152:58080",         // 后端按中继机 IP 拼
  "users": "<安装目录>/conf/users.json",
  "result_public_host": "10.10.118.152",            // AI 可达，不能是 0.0.0.0
  "result_threshold_entries": 50,
  "result_threshold_bytes": 4096,
  "mcp_timeout": 1800
}
```

### 3.3 feishu_bridge（飞书桥）—— 多 bot + 热更新

**作用**：一个进程管多个飞书机器人，每个 bot 独立线程。

**每个 bot 的独立配置：**

| 字段 | 来源 | 说明 |
|---|---|---|
| `name` | 页面填 | **同时是 relay 通道名，必须唯一** |
| `app_id` | 页面填 | 飞书应用 ID |
| `app_secret` | 页面填 | 飞书应用密钥 |
| `relay_url` | **自动拼** | `ws://<中继机IP>:<端口>/<name>` |
| `http_bind_ip` | **自动拼** | 中继机 IP（桥自己就在中继机上） |
| `inbox_dir` | **自动拼** | `inbox_<name>` |

**为什么后三个要自动拼？**
历史上 `name` 和 `relay_url` 里的通道名不一致，导致飞书报
**「没有可用的 Chat Worker」** —— 消息发到了不存在的通道。自动拼根除这个错。

**热更新**：每 **3 秒**重读配置，diff 后自动增/删/重启 bot。**改配置不用重启进程。**

**三个必须注意的点**（都是踩过的坑）：

1. **每个 bot 连各自独立的 relay 通道** —— 共用会互相踢人
2. **`http_port` 全局唯一** —— 但所有 bot **共用同一个文件服务**，按 `/<bot名>/` 路由
3. **`http_bind_ip` 填桥自身/中继机 IP**，**不是** Copilot 那边的 IP

**文件服务**：`http://<绑定IP>:8081/<bot名>/xxx`，用于飞书收发文件/图片。

**inbox 自动清理**：定期清理 `inbox_<name>/`，超天数或超数量时删最旧。

**命令**：

```bash
feishu_bridge.exe --config conf/feishu_config.json --log-path logs/feishu.log
```

---

### 3.4 nlp_worker_acp（Copilot 驱动）

**作用**：用 **ACP 协议**驱动 `copilot --acp` 常驻会话。

| 特性 | 说明 |
|---|---|
| 常驻会话 | 会话持久化到 `<cwd>/.nlp_session.<用户>.json`，**重启自动恢复** |
| 通道 | 连 relay 的 `nlp_worker` 槽 |
| 开发笔记 | `<cwd>/开发笔记.md` |
| `--bridge-http` | **必配**，否则截图/文件不回传 |
| 模型注入 | `start_nlp_copilot.bat` 注入模型配置，退出自动清空 |

## 四、部署管理器（kanzi-deployer）

### 4.1 它解决的问题

手工部署要敲一堆命令、改一堆配置、还容易写错端口和 IP。
部署管理器把这些**收成一个网页**。

### 4.2 模块结构

```
mcp_server/deployer/
├── deployer.py              主入口：启动 Web + 版本轮询 + 健康监控
├── deployer_config.json     管理器自己的配置
├── build.bat                打包成 kanzi-deployer.exe
├── docs/
│   ├── 使用手册.md
│   └── 整体架构文档.md        ← 本文
├── core/                    核心逻辑（不依赖 Web 层）
│   ├── config.py            配置加载/保存/默认值
│   ├── paths.py             目录结构管理
│   ├── gitops.py            git 操作（查最新 tag / clone / checkout）
│   ├── builder.py           PyInstaller 编译三组件
│   ├── deploy.py            部署/升级编排（核心流程）
│   ├── process.py           进程管理（启动/停止/重启/状态）
│   ├── health.py            健康检查（WS 握手 / HTTP / 进程）
│   ├── monitor.py           组件健康监控（挂了→飞书通知）
│   ├── notify.py            飞书通知（urllib 直调，零依赖）
│   ├── templates.py         从页面配置生成组件配置文件
│   ├── envcheck.py          环境检测（Python/PyInstaller/git）
│   └── logs.py              日志读取/清空/轮转信息
└── web/                     Web 层
    ├── server.py            HTTP server + 路由 + Basic Auth
    ├── api.py               各接口实现
    ├── tasks.py             异步任务管理（部署/升级进度）
    ├── auth.py              Basic Auth 校验
    └── static/
        ├── index.html       页面骨架
        ├── app.js           前端逻辑（向导/总览/配置/日志）
        └── style.css        样式
```

### 4.3 部署编排流程（`core/deploy.py::do_deploy`）

```
  2%  检查环境           Python / PyInstaller / git 是否可用
 10%  拉取源码           git clone / checkout 到 src/
 20%  源码就绪
 22%  备份现有程序        bin/*.exe → _backup/
 25%  开始编译           PyInstaller 编译三个组件
 70%  编译完成
 71%  检查组件配置        conf/ 下的配置文件是否齐全
 73%  配置就绪
 76%  停止旧进程          按反序停：feishu → http → relay
 82%  部署新程序          ★ 覆盖前先杀残留 + 等文件句柄释放
 86%  替换组件完成
 90%  启动组件            按顺序启：relay → http → feishu
 95%  健康检查            按各组件真实协议探测
100%  全部正常 / ⚠️ 未通过
```

**失败自动回滚**：任何一步失败 → 从 `_backup/` 恢复上一版本 exe。

### 4.4 关键机制

**① 探活按真实协议走**（不能一刀切）

| 组件 | 协议 | 探测 |
|---|---|---|
| relay | WebSocket | 发真握手 |
| http | 裸 HTTP | 发 GET，收到任何响应即健康 |
| feishu | 进程 | 查进程名 |

**② 进程真停才继续**

`taskkill` 是**异步**的 —— 返回 0 **不代表进程已死**。
所以：

- `kill_by_name()`：`taskkill /F /T /IM <name>` 后**轮询 `tasklist`** 直到查不到
- `wait_file_free()`：用 `r+b` 试打开探测文件句柄是否真释放（最多等 20 秒）

**这是 `[WinError 5] 拒绝访问` 的根因所在。**

**③ 版本号真相来源**

本地版本 = 源码目录 `git describe --tags --exact-match HEAD`。
不用 state 缓存的值（`state.current_tag` 只作兜底）。

**④ 后台轮询只查不升**

每 60 秒查一次远端 tag。发现新版 → 记 state + **通知一次**
（按 `notified_tag` 去重，否则每分钟骚扰一条）。
**绝不自动升级**（`auto_upgrade` 保留字段，默认 false）。

**⑤ 健康监控只通知不重启**

每 30 秒查三组件，**状态翻转才通知**（挂→好 / 好→挂），
启动后 **90 秒冷静期**内不报警（组件还在起）。

**为什么不做自动重启？** 配置错了会一直挂，自动重启就是**无限重启 + 刷日志**。

### 4.5 Web 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/status` | 总览：版本、组件状态、健康、环境 |
| GET | `/api/check_update` | 查远端最新版本 |
| POST | `/api/upgrade` | 升级（未部署/已最新会被拦） |
| POST | `/api/deploy` | 一键部署（缺配置 → 409 + 弹窗跳配置页） |
| POST | `/api/restart` | 重启指定组件 |
| GET/POST | `/api/config?name=` | 读/写配置文件（deployer/http/users/feishu） |
| GET/POST | `/api/wizard` | 配置向导（**只有 POST**，没有 PUT） |
| GET | `/api/task` `/api/tasks` | 异步任务进度 |
| GET | `/api/env` | 环境检测 |
| GET/POST | `/api/logs` `/api/logs/clear` | 日志读/清 |
| POST | `/api/test_notify` | 发测试通知 |
| POST | `/api/restart_self` | 管理器自重启 |

### 4.6 配置的生成关系（单向）

```
页面配置（deployer_config.json）
        │
        │  core/templates.py::write_all()
        ▼
conf/config.json         ← http 组件读
conf/users.json          ← http 组件读（热更新）
conf/feishu_config.json  ← feishu_bridge 读（3 秒热更新）
```

> 🔴 **单向**：手改 `conf/` 下的文件会在下次部署时**被覆盖**。
> 要改就在页面改。

## 五、Kanzi Studio 侧

### 5.1 KzMCPChatPlugin（C#）

内嵌在 Kanzi Studio 里的聊天窗口（WPF 插件）。

| 文件 | 职责 |
|---|---|
| `KzMCPChatPlugin.csproj` | 工程 |
| `KzMainWindow.xaml(.cs)` | 主聊天窗口 |
| `KzMCPServerWindow.xaml(.cs)` | 服务窗口 |
| `KzMCPServerClient.cs` | 与 relay 的 `server` 槽连接 |
| `KzWSClient.cs` | WebSocket 客户端 |
| `KzMCPReflectionBridge.cs` | **反射桥** |
| `KzSettings.cs` | 设置 |

### 5.2 KzMCPPlugin 的「全反射」铁律

**所有 Kanzi API 调用必须通过纯反射实现：**

- ❌ 不缓存 `MethodInfo` / `PropertyInfo`
- ❌ 不直接引用任何 `Rightware.Kanzi.*` 具体类型
- ✅ 方法查找一律走运行时 `FindMethod()` / `GetMethods()` / `InterfaceMapping`
- ✅ 便捷方法（`CreateNode`、`SetProperty` 等）只是**参数预处理**，
  最终都走 `Invoke` 统一入口

**为什么？** Kanzi 的版本差异大，直接引用类型会在换版本时编译不过/运行崩。
纯反射让它**跨版本可用**。

### 5.3 MCP 工具层次

```
kz_invoke(target, method, args)      ← 万能调用（最底层，什么都能干）
kz_ref_properties(target)            ← 查对象的属性
kz_enum_all_windows()                ← 枚举窗口（截图找 PID 用）
kz_screenshot_preview(pid, maxSide)  ← 截图
kz_loc_entry_*                       ← 本地化条目 CRUD
...
```

高层的 `kz_*` 便捷工具，本质都是把参数预处理后调 `kz_invoke`。

### 5.4 截图链路

```
Copilot → kz_enum_all_windows        → 拿到 Kanzi Studio 主窗 PID
Copilot → kz_screenshot_preview(pid, maxSide)
        → Kanzi 插件截屏
        → base64 PNG 返回
        → 太大？被 kz_mcp_http 外置成文件 URL
        → Copilot 取 URL → 用户看到图
```

## 六、部署拓扑与顺序

### 6.1 典型拓扑（内网）

```
┌─────────────────────────────────────────────────┐
│  中继机 10.10.118.152（Windows）                 │
│                                                   │
│   relay_multi.exe       :58080   ← 中枢           │
│   kz_mcp_http.exe       :9001                    │
│   feishu_bridge.exe     :8081    （文件服务）     │
│   kanzi-deployer.exe    :9100    （管理页面）     │
│                                                   │
│   conf/  logs/  bin/  src/  tmp_results/          │
└────────┬──────────────────────────┬──────────────┘
         │                          │
         │ (Copilot 可在同机或另一台) │ (Kanzi Studio 可在另一台)
         ▼                          ▼
┌──────────────────┐      ┌────────────────────────┐
│ Copilot 执行机   │      │ Kanzi Studio 机         │
│ nlp_worker_acp   │      │ KzMCPChatPlugin 插件    │
└──────────────────┘      └────────────────────────┘
         ▲
         │ 飞书服务器
         ▼
┌──────────────────┐
│ 飞书 App（用户）  │
└──────────────────┘
```

> ⚠️ **跨机时 `kz_mcp_http` 必须绑 `0.0.0.0:9001`**，
> 不能绑 `127.0.0.1` —— 否则 Copilot 在另一台机连不进来。

### 6.2 启动顺序（必须遵守）

```
① relay_multi        ← 中枢，必须先起
② kz_mcp_http        ← 要连 relay
③ nlp_worker_acp     ← 要连 relay（Copilot）
④ feishu_bridge      ← 要连 relay
⑤ Kanzi Studio 插件  ← 以 server 角色连 relay
```

**部署管理器会按这个顺序自动启**（`START_ORDER = ["relay", "http", "feishu"]`），
停止时按反序。

### 6.3 端口清单

| 端口 | 组件 | 用途 |
|---|---|---|
| 58080 | relay | WebSocket 中继（可用 `--port` 改） |
| 9001 | kz_mcp_http | MCP over HTTP |
| 8081 | feishu_bridge | 飞书文件服务 |
| 9100 | kanzi-deployer | 管理页面 |

## 七、关键设计决策

### 7.1 为什么用「中继」而不是点对点？

| 点对点 | 中继 |
|---|---|
| N 个客户端 × M 个 Kanzi = N×M 连接 | N+M 连接 |
| 每个客户端要知道 Kanzi 地址 | 客户端只需知道中继地址 |
| Kanzi 换了 IP 全要改 | 只改中继配置 |
| 鉴权分散 | 鉴权集中 |

**中继 = 解耦 + 集中管理。**

### 7.2 为什么按「URL 路径」分通道？

- **简单**：`ws://host:58080/<用户名>`，不用额外协议
- **直观**：浏览器/客户端工具都能直接调
- **隔离**：不同用户的通道完全独立

### 7.3 为什么 nlp_client 只允许 1 个连接？

用户输入是**串行**的 —— 两个前端同时说话会打架。
新连接踢旧的（保证最新前端可用）。

而 `client` 槽**允许多连接**，因为 Copilot 可能并发发多个 MCP 请求，
需要**定向回传**（`route` 表记 `请求id → 连接`）。

### 7.4 为什么健康检查要「按协议探测」？

**一刀切必然出错。** 真实教训：

> v10 让 `port` 类型默认发 WebSocket 握手 → 对 http 组件（裸 HTTP）
> **必然失败**，部署报「健康检查未通过」，但组件其实是好的。

修法：`port` 默认**纯 TCP**，只有 `ws: True` 才发握手；http 用 HTTP 探测。

### 7.5 为什么探活不能让被探对象日志变脏？

真握手 3 次 = websockets 库记 3 条 `connection open`。
健康检查 30 秒一轮 → **日志被淹没，真错误看不见了**。

修法：**库日志压到 WARNING**（压掉连接开合，保留握手失败等真错误）。
**压日志 ≠ 关日志** —— 真出错的可见性必须保住。

### 7.6 为什么升级不自动？

> 自动升级 = 半夜把生产环境升挂，还没人知道。

**点按钮才升**，且升级中不中断在跑的任务。

### 7.7 为什么健康监控不自动重启？

配置错了会一直挂 —— 自动重启就是**无限重启 + 刷爆日志**。
**只通知，让人来判断。**

### 7.8 为什么 Kanzi 插件必须全反射？

Kanzi 版本差异大。直接引用类型 → 换版本就编译不过。
纯反射 → 跨版本可用。

## 八、故障排查地图

### 8.1 按「消息卡在哪一环」定位

```
用户在飞书说话了，但没反应
   ↓
① feishu_bridge 收到消息了吗？        → 看 logs/feishu.log
   ↓ 没有
   桥配置对不对？bot 名和通道名一致吗？
   ↓ 有
② relay 转给 Copilot 了吗？           → 看 logs/relay.log
   ↓ 没有
   Copilot（nlp_worker）连上 relay 了吗？通道名对吗？
   ↓ 有
③ Copilot 处理了吗？                  → 看 Copilot 日志
   ↓ 处理了，但 Kanzi 没动
④ kz_mcp_http 收到请求了吗？          → 看 logs/http.log
   ↓ 403
   白名单里有没有这个用户？
   ↓ 有
⑤ relay 转给 Kanzi 了吗？
   ↓ 没有
   Kanzi Studio 插件连上 relay 了吗？（server 槽）
   ↓ 连上了，但没反应
⑥ 看 Kanzi Studio 侧
```

### 8.2 常见症状速查

| 症状 | 最可能的原因 |
|---|---|
| 飞书报「没有可用的 Chat Worker」 | **bot 名 ≠ relay 通道名** |
| http 组件起不来 | **白名单为空**（`sys.exit(1)`） |
| Copilot 连不上 http | `listen` 不是 `0.0.0.0`（绑了 127.0.0.1） |
| AI 拿不到外置文件 | `result_public_host` 填了 `0.0.0.0` 或填错 IP |
| 部署报「健康检查未通过」 | v11 之前：对 http 误发握手；之后：查端口/白名单/日志 |
| 升级报 `WinError 5` | 进程残留 / 文件句柄没释放 |
| relay 日志被 `connection open` 刷屏 | v11 之前：库 INFO 日志没压 |
| 组件「看起来在跑」但页面报挂 | 探活方式与真实协议不符 |
| 飞书收不到通知 | 设置页三字段没配全 / 权限不足 / 接收人 ID 类型不对 |

### 8.3 通用排查步骤

1. **看部署管理器总览页** —— 组件状态 + 健康检查一眼看到
2. **看具体组件日志** —— `logs/` 下四个文件
3. **看进程在不在** —— `tasklist | findstr relay_multi`
4. **看端口通不通** —— `netstat -ano | findstr 58080`
5. **看通道名一致性** —— bot 名 / 用户名 / 通道名三者必须相同

### 8.4 手动清进程（升级失败时）

```bat
taskkill /F /T /IM relay_multi.exe
taskkill /F /T /IM kz_mcp_http.exe
taskkill /F /T /IM feishu_bridge.exe
```

清完再点升级。
