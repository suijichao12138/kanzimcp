## 一、这是什么

`kanzi-deployer` 是一个**常驻 Windows 程序**。启动后会在局域网提供一个网页，
你在浏览器里就能完成原来要手敲命令行的所有事：

| 能力 | 说明 |
|---|---|
| **首次部署** | 填配置 → 一键拉源码 → 编译 → 生成组件配置 → 启动 |
| **版本升级** | 查看远端最新版本，**点按钮才升级**（不自动升，不中断在跑的任务） |
| **进程管理** | relay / http / feishu 单独重启、全部重启 |
| **配置管理** | 网页编辑三个组件的配置文件，保存后按需重启 |
| **日志查看** | relay / http / feishu / deployer 四个日志分开看，可清空 |
| **健康监控** | 组件挂了或恢复 → 飞书通知（**只通知，不自动重启**） |
| **环境自检** | Python / PyInstaller / git 是否可用，缺什么一眼看到 |

### 它管理的三个组件

| 组件 | 程序 | 作用 | 端口（默认） |
|---|---|---|---|
| **relay** | `relay_multi.exe` | WebSocket 中继，按路径分通道、多角色转发 | 58080 |
| **http** | `kz_mcp_http.exe` | MCP over HTTP 端点（给 Copilot 连） | 9001 |
| **feishu** | `feishu_bridge.exe` | 飞书 ↔ Copilot 桥（多 bot，文件服务） | 8081 |

**启动顺序固定：relay → http → feishu**（停止按反序）。
因为 http 要连 relay、feishu 要连 relay，relay 必须先起来。

## 二、五分钟上手

### 1. 启动

双击 `kanzi-deployer.exe`，或在命令行：

```bat
kanzi-deployer.exe
```

**命令行参数：**

| 参数 | 作用 |
|---|---|
| `--config <路径>` | 指定配置文件（默认：安装目录下 `deployer_config.json`） |
| `--no-web` | 不启动网页，只跑后台版本轮询 |
| `--check-update` | 只查一次远端版本后退出（脚本用） |
| `--test-notify` | 只发一条飞书测试通知后退出 |
| `--version` | 打印版本号 |

### 2. 打开网页

启动日志会打印访问地址：

```
🌐 管理页面: http://0.0.0.0:9100
   局域网访问: http://10.10.118.152:9100
```

浏览器打开 **`http://<中继机IP>:9100`**。

### 3. 登录

首次启动会**自动生成随机密码**并打印在日志里（只打印一次，注意保存）：

```
🔑 首次启动，已生成访问密码: xxxxxxxx
```

用户名默认 `admin`。登录后可到 **设置** 页改密码。

> ⚠️ 如果日志提示「尚未设置访问密码」，说明密码为空，
> **局域网内任何人都能改你的配置** —— 立刻去设置页设一个。

## 三、首次部署（配置向导）

第一次打开且没部署过时，页面会自动进入**配置向导**。三步：

### 第 1 步：组件参数

**① 中继机 IP**（最关键的一项）

填**中继机自己的内网 IP**（如 `10.10.118.152`）。
所有组件的连接地址都由**这一项自动拼接**，页面不让你手填，避免写错：

| 自动拼接项 | 结果 |
|---|---|
| http 的 relay 地址 | `ws://<中继机IP>:58080` |
| 飞书 bot 的中继通道 | `ws://<中继机IP>:58080/<bot名>` |
| 桥的文件服务绑定 IP | `<中继机IP>` |

**② http 组件**

```
监听地址填 0.0.0.0 才能让远程 Copilot 连进来；改成 127.0.0.1 则只能本机连。
  监听地址 [0.0.0.0]      端口 [9001]
```

**③ http 白名单**

一行一个用户名，**用户名 = relay 通道名**。比如填：

```
suijichao
zhenghaitao
```

就会生成两个通道 `ws://<IP>:58080/suijichao`、`.../zhenghaitao`。

> 🔴 **白名单不能为空！** 为空时 http 组件会**直接退出**（`sys.exit(1)`），
> 部署必然失败。页面会提前拦住你。

**④ 飞书桥**

```
两个 bot 共用一个文件服务：0.0.0.0 = 所有网卡都监听（推荐）。
  文件服务监听 IP [0.0.0.0]    文件服务端口 [8081]
```

然后是 **bot 列表**，每个 bot 只填 **3 项**：

| 字段 | 说明 |
|---|---|
| **Bot 名称** | 同时是 relay 通道名，**必须唯一** |
| **App ID** | 飞书应用的 App ID |
| **App Secret** | 飞书应用的 App Secret（显示为掩码，不改就保留原值） |

其余字段（`relay_url` / `http_bind_ip` / `inbox_dir`）**全部由后端按名称自动拼**，
不用你操心 —— 历史上正是因为这两者不一致，飞书才报「没有可用的 Chat Worker」。

**⑤ inbox 自动清理**

```
启用填 true / false；保留天数 / 保留数量 / 扫描间隔都可留空 = 继承上一级。
  启用 [ ]   保留天数 [ ]   保留数量 [ ]   扫描间隔(秒) [ ]
```

| 字段 | 含义 | 默认 |
|---|---|---|
| 启用 | 是否开启自动清理 | `true` |
| 保留天数 | 超过这么多天的 inbox 文件被删 | `7` |
| 保留数量 | 目录内最多留几个文件，超出删最旧 | `500` |
| 扫描间隔(秒) | 多久扫一次 | `3600` |

### 第 2 步：飞书通知（可选但强烈建议）

配置**部署管理器自己**发的通知（和飞书桥的 bot 不是一回事，详见下节）：

| 字段 | 必填 | 说明 |
|---|---|---|
| App ID | ✅ | 飞书应用 ID |
| App Secret | ✅ | 飞书应用密钥 |
| 接收人 ID | ✅ | 谁收通知（`open_id` 形式，如 `ou_xxxx`） |
| 接收人 ID 类型 | | 默认 `open_id` |

填完点 **「测试」**，飞书收到一条测试消息说明链路通了。

### 第 3 步：确认并部署

点 **「一键部署」**，页面会依次走：

```
检查环境 → 拉取源码 → 备份现有程序 → 编译 → 生成配置
        → 停止旧进程 → 部署新程序 → 启动组件 → 健康检查
```

**进度条会实时显示每一步。** 全绿就成功了。

## 四、日常操作

### 总览页

一眼看到：

- **本地版本 / 远端最新版本**
- **三组件运行状态**（运行中 / 已停止）
- **健康检查结果**（每个组件是否真的能通）
- **环境是否就绪**

### 升级

1. 后台每 60 秒自动查一次远端版本（**只查，不升**）
2. 发现新版本 → 总览页出现提示 + 飞书通知一条（**同一版本只通知一次**）
3. 你点 **「升级」** → 二次确认 → 开始升级

**升级按钮在以下情况置灰：**

- 还没部署过（先走首次部署）
- 已经是最新版本
- 有任务正在跑

### 配置管理

| 文件 | 内容 | 保存后 |
|---|---|---|
| `deployer_config.json` | 管理器自己的配置 | 需重启管理器 |
| `conf/config.json` | http 组件配置 | 重启 http 组件 |
| `conf/users.json` | http 白名单 | **热更新，不重启** |
| `conf/feishu_config.json` | 飞书桥配置 | **热更新，不重启**（桥每 3 秒重读） |

> ⚠️ **配置页保存是「整份覆盖」** —— 用手改磁盘文件没用，
> 下次部署会被页面配置重新生成覆盖。要改就在页面改。

### 进程管理

- **单组件重启**：某个组件配置改完，单独重启它
- **全部重启**：按 relay → http → feishu 顺序重启
- **停止**：先按反序停止

重启/停止会**等进程真正退出、文件句柄真正释放**才继续（避免
`[WinError 5] 拒绝访问` —— 旧版就是因为 `taskkill` 是异步的，返回 0 不代表进程已死）。

### 日志

四个日志页：`relay` / `http` / `feishu` / `deployer`。
各组件用 `RotatingFileHandler` **自己轮转**（10MB × 5 个备份），
**轮转过程不中断服务**。支持一键清空。

## 五、配置项说明

### 5.1 管理器配置 `deployer_config.json`

```jsonc
{
  "paths":   { "bin": "bin", "conf": "conf", "logs": "logs",
               "src": "src", "tmp": "tmp_results",
               "data": "data", "backup": "_backup" },

  "web":     { "bind": "0.0.0.0", "port": 9100,
               "auth": { "enabled": true, "user": "admin",
                         "password_sha256": "" } },

  "monitor": { "enabled": true,       // 组件健康监控开关
               "interval_s": 30,      // 检测间隔（秒）
               "grace_s": 90 },       // 启动后冷静期（秒）

  "repo":    { "url": "https://gitee.com/suijichao/kanzimcp.git",
               "branch": "main",
               "use_tag": true,       // 按 tag 判版本
               "poll_interval_s": 60, // 版本轮询间隔
               "auto_upgrade": false }, // 保留开关，默认关

  "build":   { "python_exe": "python",
               "pyinstaller": "pyinstaller",
               "timeout_s": 1800 },

  "kill_wait_ms": 2000,               // 杀进程等待
  "health":  { "timeout_s": 30,       // 健康检查总等待
               "interval_s": 5 },     // 探测间隔

  "log":     { "max_bytes": 10485760, "backup_count": 5 },

  "feishu_notify": { "enabled": true, "app_id": "", "app_secret": "",
                     "receive_id": "", "receive_id_type": "open_id" },

  "comp_params": { /* 见下 */ },
  "users": []
}
```

### 5.2 组件参数 `comp_params`

```jsonc
{
  "http": {
    "listen_host": "0.0.0.0",            // → listen: "0.0.0.0:9001"
    "listen_port": 9001,
    "mcp_timeout": 1800,
    "heartbeat_interval": 30,
    "heartbeat_max_fails": 3,
    "req_check_interval": 2,
    "result_ttl": 1800,
    "result_public_host": "",            // 外置结果 URL 用的 IP，后端自动填
    "result_threshold_entries": 50,      // 超过这么多条 → 落盘
    "result_threshold_bytes": 4096       // 超过这么多字节 → 落盘
  },
  "relay":  { "port": 58080 },           // relay 无配置文件，仅端口

  "feishu": {
    "http_host": "0.0.0.0",              // 共享文件服务绑定
    "http_port": 8081,
    "cleanup": { "enabled": true, "max_age_days": 7,
                 "max_files": 500, "interval_s": 3600 },
    "bots": []                           // 页面只填 3 项，其余自动拼
  }
}
```

**http 外置结果**：MCP 返回内容超过阈值（50 条 / 4096 字节）时，
自动落盘成文件、只回一个 URL 给 AI —— 截图 base64 必然超，会被外置。

**`result_public_host` 必须 AI 能访问到**，所以后端填的是**中继机 IP**，
**绝不能填 `0.0.0.0`**。

### 5.3 组件配置（自动生成，勿手改）

| 生成文件 | 来源 |
|---|---|
| `conf/config.json` | http 组件（`listen` / `relay_base` / `users` / 外置阈值…） |
| `conf/users.json` | 白名单 `{"users": ["suijichao", ...]}` |
| `conf/feishu_config.json` | `reload` / `http` / `cleanup.inbox` / `bots[]` |

**bot 的 6 个字段**（页面填 3 个，其余自动）：

```jsonc
{
  "name": "suijichao",                                  // 你填
  "app_id": "cli_xxx",                                  // 你填
  "app_secret": "xxx",                                  // 你填
  "relay_url": "ws://10.10.118.152:58080/suijichao",    // 自动拼
  "http_bind_ip": "10.10.118.152",                      // 自动拼
  "inbox_dir": "inbox_suijichao"                        // 自动拼
}
```

### 5.4 两类「飞书」配置的区别（容易混，务必分清）

| | 管理器飞书通知 | 飞书桥 Bot |
|---|---|---|
| 页面位置 | **设置页 → 飞书通知** | **配置页 → 飞书桥 → Bot 列表** |
| 存储位置 | `deployer_config.json` → `feishu_notify` | `conf/feishu_config.json` → `bots[]` |
| 谁在用 | **kanzi-deployer 自己** | **feishu_bridge 组件** |
| 用途 | **只发不收**：部署/升级/告警通知 | **双向**：收飞书消息驱动 Kanzi |
| 数量 | 1 个 | 多个 |

**简单记：设置页那个是「我（部署器）怎么告诉你」，配置页那个是「飞书机器人怎么转发消息」。**

## 六、日志与排查

### 日志文件

```
logs/deployer.log    管理器自己
logs/relay.log       中继
logs/http.log        MCP over HTTP
logs/feishu.log      飞书桥
```

### 通知覆盖范围

| 事件 | 通知 |
|---|---|
| 部署成功 / 失败 | ✅ |
| 升级成功 / 失败 | ✅ |
| 发现新版本 | ✅（按版本去重，同一版本只发一次） |
| 组件挂了 / 恢复 | ✅（状态翻转才发，持续挂着不重复） |
| 环境不满足 | ✅（走失败通知，带上缺什么） |

### 组件健康监控

- **间隔 30 秒**检测一次
- **冷静期 90 秒**：刚启动组件还在起，这期间不报警（避免一开机报三条）
- **只在状态翻转时通知**：正常→挂 发「❌ 组件异常」，挂→正常 发「✅ 组件恢复」
- **只通知不重启**（有意设计：自动重启有「配置错了一直挂还刷日志」的风险）
- 想关掉：配置里 `"monitor": {"enabled": false}`

### 探测方式按服务的真实协议走

| 组件 | 真实协议 | 探测方式 |
|---|---|---|
| relay | WebSocket | 发真握手 |
| http | **裸 HTTP**（`asyncio.start_server`） | 发普通 HTTP 请求，收到任何响应即健康 |
| feishu | 进程 | 查进程是否存在 |

> ⚠️ **http 组件不是 WebSocket 服务** —— 对它发 WebSocket 握手会失败。
> 这是 v10 的一个真实教训，v11 已修。

## 七、常见问题 FAQ

### ❓ 页面点「一键部署」没反应 / 弹窗按钮点不动

**v13 已修**。旧版根因：弹窗 DOM 写在 `<script>` 之后，
绑定事件时元素还不存在。升级到 v13+ 即可。

### ❓ 部署报「健康检查未通过」，但组件日志看起来正常

**v11 已修**。旧版对 http 组件误发 WebSocket 握手 → 必然失败（假失败）。
现在 http 用 HTTP 探测。

如果仍然失败，检查：

1. 白名单是否为空（**为空 http 组件直接退出**）
2. 端口是否被别的程序占用
3. 看 `logs/http.log` 有没有真错误

### ❓ 升级报 `[WinError 5] 拒绝访问`

**v10 已修**。旧版 `taskkill` 是异步的，返回 0 ≠ 进程已死。
新版会**轮询确认进程真的没了、文件句柄真的释放了**才覆盖。

**如果还是遇到**，先手动清一遍进程再升级：

```bat
taskkill /F /T /IM relay_multi.exe
taskkill /F /T /IM kz_mcp_http.exe
taskkill /F /T /IM feishu_bridge.exe
```

### ❓ 飞书报「没有可用的 Chat Worker」

**bot 名称和 relay 通道名不一致**。这两个必须相同。
页面已自动按名称拼接通道地址，别手改 `relay_url`。

### ❓ 收不到飞书通知

1. 设置页的 `App ID` / `App Secret` / `接收人 ID` 三个都填了吗
2. 点「测试」看能否收到
3. 飞书应用需要 `im:resource` 和发送消息权限
4. 接收人 ID 类型要跟 ID 形式匹配（`open_id` 对应 `ou_xxx`）

### ❓ relay 日志被 `connection open` 刷屏

**v11 已修**。这是 `websockets` 库的 INFO 日志，被健康检查频繁触发。
现在库日志压到 WARNING：**`connection open` 没了，真错误（握手失败等）还在**。

### ❓ 升级后组件还是旧版本

三个组件是**编译出来的 exe**。升级流程会重新编译，但要确认
PyInstaller 环境可用（总览页的「环境」区会显示）。

### ❓ 页面卡 / 转圈很久

**v13 已修**。旧版一键部署会先串行探活 3 个组件（每个 1.5 秒超时），
现在改为后端兜底 + 探活结果加缓存。

### ❓ 白名单改了要重启吗

**不用**。`conf/users.json` 是热更新的，http 组件会自己重读。

### ❓ 飞书桥的 bot 改了要重启吗

**不用**。桥每 **3 秒**重读一次配置文件，自动增/删/重启 bot。

## 八、升级与回滚

### 升级流程

```
点「升级」→ 二次确认
   ↓
检查环境 → 备份现有 exe 到 _backup/ → 拉取新版本源码
   ↓
编译 → 停止旧进程 → 覆盖 exe → 启动 → 健康检查
   ↓
失败？→ 自动回滚（从 _backup/ 恢复）
```

### 回滚

升级过程中任何一步失败，会自动从 `_backup/` 恢复上一版本 exe。

> ⚠️ 回滚前也会**先杀残留进程、等文件释放** —— 旧版就是因为回滚自己
> 也被 `WinError 5` 挂掉，还把异常吞了，导致 `bin/` 变成**半新半旧**。

### 手动回滚

`_backup/` 里存的是升级前的 exe。要手动回滚：停掉三个组件 →
把 `_backup/` 里的文件复制回 `bin/` → 重启。

## 九、注意事项

### 🔴 部署前必须确认

1. **白名单不能为空** —— 为空 http 组件直接退出
2. **中继机 IP 要填对** —— 所有连接地址都由它拼出来
3. **bot 名称必须唯一** —— 同时是 relay 通道名
4. **`result_public_host` 不能是 `0.0.0.0`** —— AI 访问不到（页面已自动处理）

### 🔴 安全

1. **务必设置访问密码** —— 否则局域网内任何人都能改配置
2. **App Secret 只在页面显示掩码** —— 提交掩码 = 保留原值，不会覆盖
3. **不要把 App Secret 发在聊天里** —— 会被 GitHub Secret Scanning 识别拦截

### 🔴 不要手改自动生成的文件

`conf/config.json`、`conf/users.json`、`conf/feishu_config.json`
都由页面配置生成。**手改会在下次部署时被覆盖。**

### 🔴 别动旧版目录

`mcp_server/ota/` 是**旧版 OTA 程序，已废弃**，仅作历史保留。
所有功能都由 `mcp_server/deployer/` 提供。
