# 报告页「修改建议」展示方案

> 版本：v1.1　日期：2026-11-27　状态：**方案设计稿（不含任何代码改动）**
>
> **优先级：低。前置依赖：`AI语义审查与覆盖率补全方案.md` 中的检查项覆盖工作全部完成后再启动。**
>
> **v1.1 修订：不新增表格列，建议仅在右侧详情面板展示。表格保持现有 6 列不变。**

## 0. 为什么优先级低

「修改建议」是**展示层增强**，它的价值取决于"有多少条 finding 能给出有意义的建议"。

- 如果检查项覆盖没做完（当前 44.6%），报告里大量条款根本定位不到，建议列对这部分**无内容可填**
- T 类 39 条、S 类 51 条补完之后，finding 数量和质量才够支撑建议列
- A 类 34 条的 AI 建议**随 AI 审查框架一起产出**，也必须等那一期完成

**结论**：先做完覆盖率补全，本方案才有意义。

## 2. 目标

在报告页详情面板新增「修改建议」区块，做到：

1. **任何一条 finding 都有建议内容**，详情面板不出现空区块
2. 建议**分级标注来源可信度**，用户能判断该不该照改
3. AI 生成的建议**必须标注【AI 判定需人工复核】**
4. **表格保持现有 6 列不变**，不加列、不挤压阅读空间
5. CSV 导出同步加两列（导出是数据文件，不受表格列限制）

## 3. 五种数据来源（按可靠性排序）

### 来源 1：引擎原生建议（最可靠，0 成本）

| 引擎 | 现成能力 | 产出 |
|---|---|---|
| **clang-tidy** | `--export-fixes=<yaml>` | 精确到字符位置的替换文本 |
| **clang-format** | `--dry-run` 输出 diff | 「应改成什么样」 |
| **cppcheck** | 无结构化建议 | 仅 `msg` 原文 |

clang-tidy 的 fixes 格式示例：

```yaml
Diagnostic:
  - Message: use nullptr
    Replacements:
      - FilePath: src/a.cpp
        Offset: 120
        Length: 1
        ReplacementText: "nullptr"
```

**这是价值最高的一档**，能直接给出可复制的替换代码。

### 来源 2：规则内置模板（自研写，1 天）

41 条自研规则 + S 类新增 51 条，每条配一个建议模板：

```python
SUGGEST = {
    "YB-No.22": "将第 {line} 行拆分为多行，每行不超过 80 列。",
    "YB-No.84": "在全局变量 '{name}' 前加 'g_' 前缀，改为 'g_{name}'。",
    "YB-No.105": "成员变量 '{name}' 改为 'm_{name}'（基础类型再加类型前缀，如 m_i{name}）。",
    "YB-No.174": "将 '{var}.size() == 0' 改为 '{var}.empty()'。",
    "YB-No.177": "将 vector<bool> 改为 std::vector<char> 或 std::bitset。",
}
```

**支持占位符**，从 finding 现有数据填充（变量名、行号、规则类别）。

### 来源 3：规范原文示例（自动化，0.5 天）

`data/spec_manual.md` 中每条款含示例：

- `**规范示例（原文「建议采用的例子」）**` → 正例
- `**反例（原文「不建议使用的例子」）**` → 反例

**可自动提取**：条款命中 → 摘该条款「规范示例」段落。
这是规范制定者自己写的改法，**权威度最高**。

### 来源 4：AI 生成建议（复用 AI 审查框架，0 额外成本）

A 类 34 条语义条款，在 AI 审查输出中加一个字段：

```json
{
  "line": 88,
  "clause": "YB-No.80",
  "hit": true,
  "reason": "变量同时用于循环计数与数组索引",
  "confidence": "中",
  "suggestion": "拆分为两个变量：i 用于循环计数，idx 用于数组索引。"
}
```

**只加一个字段，不增加额外调用**。必须在报告里标注【AI 判定需人工复核】。

### 来源 5：通用兜底（必须有，0.5 天）

任何来源都没有时，按条款类型推导：

| 条款类型 | 兜底建议 |
|---|---|
| 命名类（1/8 类） | 按规范重命名，参考同模块已有命名风格 |
| 格式类（4 类） | 运行 `clang-format -i <file>` 自动修复 |
| 内存类（12 类） | 参照规范原文 YB-No.x 的示例代码修改 |
| 注释类（5 类） | 补充说明目的与功能的注释，避免重复代码 |
| 其他 | 参见规范原文 YB-No.x |

## 4. 三级填充策略

```
每条 finding
  │
  ├─① 引擎原生建议？（clang-tidy fixes / clang-format diff）
  │     有 → 直接用
  │
  ├─② 规则模板建议？（自研 41 条 + S 类 51 条）
  │     有 → 填充模板占位符
  │
  ├─③ 规范原文示例？（spec_manual.md 自动提取）
  │     有 → 摘「规范示例」段落
  │
  └─④ 通用兜底（按条款类型）
        必有
```

**保证：任何一条 finding 都有建议内容，不会出现空列。**

## 5. UI 设计

### 5.1 表格列布局（选项 B + C 组合）

**表格保持现有 6 列，不加任何列。**

```
| 工具 | 级别 | 位置 | 规则 | 描述 | 规范 |
|------|------|------|------|------|------|
| cppcheck | 警告 | a.cpp:42 | YB-No.22 | 行宽 95 > 80 列 | YB-No.22 |
```

- 表格布局完全不变
- 点击行 → 右侧详情面板显示「修改建议」完整内容
- 详情面板是现代码审查的阅读位置，建议放在这里不挤占列表

### 5.2 详情面板增强（`report.py:362`）

现有：位置 / 规范条款 / 源码上下文

**在「规范条款」之后、「源码上下文」之前插入「修改建议」区块，并在源码上下文之后追加「规范原文示例」**：

```
修改建议  [工具修复]                    [复制]
  将第 42 行拆分为多行，每行不超过 80 列。
  ┌─────────────────────────────────┐
  │ if ((conditionA >= 0) &&        │  ← 代码块
  │     (conditionB >= 0))          │
  └─────────────────────────────────┘
  ──────────────────────────────────
  源码上下文 …（原样保留）
  ──────────────────────────────────
规范原文示例
  正例：…
  反例：…
```

区块结构示意：

```
┌─────────────────────────────────────┐
│ 修改建议                    [复制]  │
│ 将第 42 行拆分为多行，每行不超过     │
│ 80 列。                             │
│ ┌─────────────────────────────────┐ │
│ │ if ((conditionA >= 0) &&        │ │  ← 代码块
│ │     (conditionB >= 0))          │ │
│ └─────────────────────────────────┘ │
├─────────────────────────────────────┤
│ 规范原文示例                        │
│ 正例：int32_t ModuleA_SetValue(     │
│        Char *pcName, int iID);      │
│ 反例：int32_t ModuleA_SetValue(     │
│        Char *pcName, int iID );     │
└─────────────────────────────────────┘
```

### 5.3 来源标记（区分可信度）

建议前加小标签：

| suggest_src | 标签 | 配色 |
|---|---|---|
| `tool` | `工具修复` | 绿（可直接用） |
| `template` | `规则建议` | 蓝（规则模板） |
| `spec` | `规范示例` | 紫（原文权威） |
| `ai` | `【AI 判定需人工复核】` | 橙（需人核） |
| `generic` | `通用提示` | 灰（仅参考） |

### 5.4 CSV 导出同步

现有导出按钮（`report.py:237`）输出 CSV，**必须加「修改建议」和「建议来源」两列**，否则用户拿到的表格缺信息。

## 9. 验收标准

1. 任选一个真实工程跑检查，**点开任一条 finding，详情面板「修改建议」区块非空**
2. 建议来源标签正确显示（tool / template / spec / ai / generic）
3. AI 建议明显标注【AI 判定需人工复核】
4. 详情面板能看完整建议 + 可复制代码
5. CSV 导出含「修改建议」「建议来源」两列
6. **表格仍是 6 列，排版与改造前完全一致**

## 10. 风险

| 风险 | 应对 |
|---|---|
| 表格列数不变后的可发现性 | 详情面板是你点击查看的位置，建议放在这里；可考虑在描述列加小图标提示 |
| clang-tidy fixes 位置漂移 | 以 Offset 为准，不改源码只展示 |
| 模板建议与规范不一致 | 模板文案必须逐条对照 `spec_manual.md` |
| AI 建议误导用户 | 强制标注 + 橙色区分 + 不计入正式问题 |
