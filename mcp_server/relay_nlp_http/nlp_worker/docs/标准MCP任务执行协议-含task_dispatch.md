# 标准 MCP 任务执行协议（含 task_dispatch 子会话派发）

> 用途：从「读需求」到「全部完成」的完整标准流程。
> 默认使用低 Token 模式：只在需求确认、规划包确认、执行批次结束和最终验收时等待用户检查。
> 复制本文件到新任务目录，替换 <占位符> 即可使用。

## 0. 执行总则

1. 严格按阶段顺序执行。
2. 仅在以下检查点停止：阶段 1、阶段 2、阶段 4、阶段 6。用户回「继续」后进入下一检查点。
3. 用户指出修改点时，只读取和修订相关章节，不重新加载或输出完整文档。
4. 加载的 skill 可以完全确认，未知 kanzi 项优先通过 kanzi-skill-mcp 加载当前工作直接需要的 skill，返回的 skill 完全可以确认；禁止预先读取全部 skill。已确认的 API 用法直接复用，只有接口未知或调用失败时才查询方法和属性。
5. 不使用固定 @obj 编号；句柄只在当次调用返回中使用，跨阶段一律写回状态文件再读取。
6. **@obj 引用按工程隔离**——`kz_select_project` 切换工程会清空上一工程的引用缓存；因此 cachedRefs / prefetchPlan 全部按工程分区存储，绝不跨工程复用引用。
7. 中文字符串直接传中文，不传 \uXXXX。
8. 大输出（get_Properties / get_Options / get_Children / get_Node_Tree）一律落盘，只用 grep、定向查询或脚本提取必要字段；禁止读取完整 dump。
9. 优先使用批量 MCP 工具，一次提交同类资源或属性；禁止可合并的逐项调用和逐项读回。
10. 状态文件以稳定路径、名称和完成范围为主；@obj 仅记录当前工程、当前批次仍需复用的关键引用，不保存完整资源枚举。
11. 有关 kanzi MCP 的操作优先脚本执行。
12. 工具输出只保留成功数、失败项、关键路径和必要引用；不在回复中复述完整参数、返回值或已写入文件的清单。
13. 每个检查点完成后，将状态压缩为"已完成、未完成、异常、下一批次"四项；后续只读取该摘要和当前批次对应的文档片段。

### 🆕 0.5 任务派发总则（task_dispatch 子会话隔离，2026-10-21 老隋要求）

> **核心目标：MCP 调用的参数和结果不进入主会话上下文。**

1. **主会话负责规划**（读需求、拆任务、生成参数），**子会话负责执行 Kanzi 操作**。
2. **任何具体的 Kanzi 操作（创建/设置/查询）都不由主会话直接调 kz_* 执行**，而是：
   - 主会话把任务参数写入 `workfile/tasks/<类型>/<任务id>.json`（参数落盘，不进会话）
   - 主会话调 `task_dispatch(type=<类型>, task_file=<路径>)` 派发
   - 子会话读任务文件、执行 kz_*（参数全在子会话上下文），完成后回报 ✅/❌
3. **子会话按类型隔离复用**：`create-node` / `create-state-machine` / `create-property` / `create-resource` / `localization` / `texture` / `animation` / `binding` / `alias` / `shader` / `save-export`。同类任务用同一子会话（经验累积），类型不同用不同子会话（互不污染）。
4. **task_dispatch 调用本身只有 `type` + `task_file` 两个小字段**，主会话上下文不出现具体参数。
5. 子会话注入该类型专属 skill（config `task_dispatch.session_types` 配置）+ 通用支撑 skill。
6. 任务文件 JSON 结构（统一约定）：
   ```json
   {
     "task_type": "create-state-machine",
     "project": "<工程名>",
     "target": "<操作目标路径>",
     "steps": [
       {"action": "create_state", "name": "...", "level": 1, "parent": "..."},
       {"action": "set_property", "path": "...", "prop": "...", "value": "..."}
     ],
     "expected": "验收点描述"
   }
   ```
7. 子会话完成后回报格式（主会话只转述，不再执行）：
   - ✅ 成功：`✅ 任务完成（<类型> 子会话）—— 新建 N 个对象，清单见 <任务文件>`
   - ❌ 失败：`❌ 任务失败（<类型> 子会话）—— 第 K 步 <动作> 报错：<原因>`

## 阶段 1：读需求 → 需求理解摘要

**输入**：需求文档 <需求文档路径.md>

**要做**：
1. 读取需求文档全文。
2. 提取并列出：
   - 涉及工程（多工程按操作顺序）
   - 涉及资源（Property Type / Texture / Localization / 字体 / 状态机 / 动画）
   - 节点结构（新建/修改/删除）
   - 每个对象的属性、绑定、动画、触发器清单
   - 需保存导出的工程
3. 输出需求理解摘要（编号列出所有工作项），标注每个工作项归属哪个阶段。

**产物**：需求理解摘要（含工作项清单）

**输出结尾**：【待检查：阶段1 需求理解摘要】

---

## 阶段 2：生成 MCP 执行步骤文档

**输入**：阶段 1 通过的需求理解摘要

**要做**：
1. 按工作项顺序，生成 MCP执行步骤.md（编号章节：工程切换 → 属性 → 资源 → 节点 → 绑定 → 状态机 → 动画 → 触发器 → 验证 → 保存）。
2. 每章写明：目标、关键调用链、约束（如枚举不得重复、Animation Data 命名规则）、验证方式。
3. 参照现有规范格式（执行约束 + 分工程章节）。

**产物**：MCP执行步骤.md

**输出**：【待检查：阶段1 ：MCP执行步骤摘要】

---

## 阶段 3：生成命令序列表格

**输入**：阶段 2 通过的 MCP执行步骤.md + 命令序列表格模板.md

**要做**：
1. 严格按模板生成 命令序列表格.md：每行 = 步骤号 / 阶段 / 语义化目标 / MCP 工具 / 方法参数 / 预期结果 / 验证点。
2. 只翻译不调工具；不写死 @obj；大输出标注 → dump 临时文件 + grep。

**产物**：命令序列表格.md

**输出**：只报告文件路径和步骤数量，不等待，直接进入阶段 4。

---

## 阶段 4：分组方案

**输入**：阶段 3 通过的 命令序列表格.md

**要做**：
1. 把序列按「同工程 + 同类操作 + 可验证边界」分组，每组建议 10–30 行；仅在存在风险、依赖或不可批量验证时拆小。
2. 典型分组：工程准备 / 属性定义 / 资源创建 / 节点创建 / 布局与属性 / 绑定 / 状态机 / 动画与触发器 / 分组验证 / 保存导出。
3. 输出分组表：组号 / 组名 / **所属工程** / 覆盖行号 / 组内逻辑说明 / 组结束验证点（与状态文件 groups 字段的 id/name/project/rows/status 一一对应）。
4. **组不跨工程**——每个组只操作一个工程；切换工程的边界必须落在组与组之间，不允许一个组内中途切工程。
5. 标注每组是否含「创建类」操作（CreateProjectItem / CreateBinding / AddProperty / kz_create_node 等）——这类组结束必须列新建对象清单。
6. 将连续、同工程、可安全执行的 2–5 个组组成一个"执行批次"；默认每个工程一个或少量批次。

**产物**：分组表

**输出结尾**：【待检查：阶段2–4 规划包】

---

## 🆕 阶段 4.5：任务拆解与派发（子会话隔离，替代原阶段 5 直执行）

**输入**：阶段 4 通过的分组表

**要做**：
1. 把每个组按「操作类型」归类到子会话类型（映射见阶段 0.5 第 3 条）。
2. 每个子任务：
   - 生成任务参数 JSON（结构见 0.5 第 6 条）→ 写入 `workfile/tasks/<类型>/task-NNN.json`
   - 记录 task_file 路径到状态文件 `tasks` 字段
3. 逐个调 `task_dispatch(type=<类型>, task_file=<路径>)` 派发。
4. 子会话执行期间主会话不做 Kanzi 操作；只等回报。
5. 汇总所有子会话回报 → 主会话简报（哪些类型子会话执行、成功/失败原因）。

**产物**：任务派发清单（类型 × task_file × 回报）

**输出结尾**：【待检查：阶段4.5 任务派发结果】

---

## 阶段 5：按批次验证与收尾

**输入**：阶段 4.5 完成的任务派发结果 + 状态文件

**要做**：
1. 抽查子会话回报的验证点：批量操作核对工具返回数量，再读回首项、末项和异常项；需求明确要求逐项验证时除外。
2. 大输出按标注落盘，只提取本批次需要的字段。
3. 可恢复错误只记录失败项并继续独立步骤；会影响后续依赖或可能污染工程时立即停止。
4. 每个执行批次结束：
   - 一次性更新完成范围、下一步骤、异常项和仍有效的关键引用。
   - 精简输出：完成的组号和步骤范围、新建对象数量及清单文件路径（正文只列关键对象）、验证结论和失败项。
   - 仅在批次检查点截图，不为每组重复截图。
5. 输出结尾：【待检查：批次<编号> 执行结果】

---

## 阶段 6：收尾

**输入**：所有组通过 + 保存导出 skill

**要做**：
1. 执行完整验证（按执行步骤文档的「验证」章节逐项核对）。
2. **逐工程保存导出**——对涉及修改的每个工程：
   - 若当前活动工程 ≠ 目标工程，先 `kz_select_project` 切换；
   - `@studio.get_Commands()` 取 GeneratedCommandInvoker（每次连接动态获取，不写死编号）；
   - 执行 `SaveProject("@project")`；按需 `ExportBinary("@project")`。
3. 截图回传关键视觉结果（附 [FILE] 标注）——**截图前先 `Commands.RestartPreview()` 刷新 Preview**（见 kanzi-screenshot skill）。
4. 更新状态文件为全部完成（phase=6，status 全 done）。

**产物**：验证报告 + 截图

**输出结尾**：【全部完成】

---

## 附：状态文件约定（与 会话交接状态文件模板.json 配套）

- **cachedRefs**：**按工程分区的对象** `{ "<工程名>": { "@objNNN": { "desc": "...", "path": "..." } } }`。只记录当前插件会话内有效、且属于该工程的句柄；插件/Studio 重启或**切换工程**后该分区失效需重新查询。
- **记录格式**：对象形式 `{ "desc": "...", "path": "<节点路径或资源名>" }`，带路径兜底——ref 失效时用 path 重新查询。
- **prefetchPlan**：**按工程分区**的预缓存清单 `{ "<工程名>": [ {name, query, targetPath} ] }`；每个组开始前，用本组所属工程的那份分区补齐该工程缓存。
- **currentProject**：当前活动工程；每次 kz_select_project 切换后更新。
- **newObjects**：每组执行后把新建对象（工程/类型/名称/路径/ref）追加进来，供【新建对象清单】检查。
- **groups**：记录每个组的 id/name/**project**/rows/status（done|in_progress|pending），组间切换时更新 currentGroup。
- **tasks**：任务派发清单（task_type × task_file × status × report），供阶段 4.5/5 追踪。
- 每个执行批次开始，只读状态摘要和当前批次字段，避免重复加载完整 JSON。
- 每组结束批量记录完成范围；每个批次结束再把仍有后续用途的 ref 写回对应工程分区。
- 状态文件另设精简摘要字段，固定只保留：已完成范围、当前工程、下一批次、阻塞项、关键路径。
