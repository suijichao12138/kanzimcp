# V12：多工程支持（Multiproject）设计方案

> 基线：基于 **V11_transformation2d**（NAS `v11_transformation2d/`）复制派生，V11 一行未动。
> 需求（老隋 2026-08-17）：Kanzi Studio 同时打开多个工程时，MCP 插件不仅改 ActiveProject，
> 也能改指定的其他工程。不指定工程时仍默认 ActiveProject（`@project` 行为不变）。

---

## 现状（V11 源码确认）

- bridge 构造时 `_project = _studio.ActiveProject`，全局只持有一个工程对象。
- `InvokeCore` 里 `@project`/`@projectItem` 别名、`GetNodeByPath`/`GetProjectItem`/`GetRootNode`
  全部依赖这单一 `_project` / `_projectItem`。
- `Refresh()` 重绑到 ActiveProject。
- `KanziStudio` 接口（PluginInterface.dll 反射确认）已暴露多工程能力：
  - `get_Projects` ✅ 枚举所有打开工程
  - `get_PrimaryProject` / `get_LoadedProject`
  - `set_ActiveProject` / `SaveAllProjects` / `LoadProject` / `CloseProject`
  - `ProjectOpened` / `ProjectClosed` 事件

> ⚠️ 重要基线纠正：当前正式部署架构 = **KzMCPServerClient（直连 relay，role=server）**，
> workspace 的 KzMCPHttpServer（HTTP 版）是已废弃旧线，**不是 v12 基线**。

---

## 方案 A：不切 ActiveProject（优先，侵入大一点但最干净）

保持 ActiveProject 永远是老隋正在编辑的工程，通过 `get_Projects` 拿到任意工程对象直接操作。

### A.1 工程上下文池（ProjectContext）

把 bridge 全局的 `_project`/`_projectItem`/`_projectType`/`_projectItemType` 从"单例字段"
升级为"按工程隔离的上下文"，用一个 `Dictionary<工程标识, ProjectContext>` 保存：

```csharp
class ProjectContext {
    object Project;          // 该工程的 Project 对象
    object ProjectItem;      // 该工程的 wrapped item
    Type   ProjectType;
    Type   ProjectItemType;
}
```

- `@project` 别名 → 指向**当前选中工程**的上下文（默认 = ActiveProject）
- 新别名 `@proj:<name>` → 指向指定工程，如 `@proj:hmi-alarm`

### A.2 新增工具（KzMCPServerClient 分发层加）

```
kz_list_projects            → [{name, isActive, ref}, ...]（调 @studio.get_Projects 枚举）
kz_select_project {name}    → 设置"当前工程上下文"；name 空=切回 ActiveProject
```

### A.3 target 前缀支持

`ResolveObject` / `InvokeCore` / `GetNodeByPath` / `GetProjectItem` 增加对
`@proj:<name>:<path>` 前缀的解析：先取指定工程上下文，再在该工程内解析路径。

### 优点
- 完全不打扰 ActiveProject / 老隋正在编辑的工程
- 语义清晰：`@project`=默认（ActiveProject），`@proj:<名>`=指定

### 代价
- bridge 改动较大：所有依赖 `_project` 的私有方法要改为"带工程上下文参数"或"先用当前上下文"
- 需实测 `get_Projects` 返回的非活跃工程对象能否直接 CreateProjectItem / SaveProject

---

## 方案 B：内部临时切 ActiveProject（侵入最小，但有副作用）

不引入工程池，仍用桥的单一 `_project`。新增 `kz_select_project` 内部执行：

```
记下原 ActiveProject → set_ActiveProject(目标工程) → bridge._project 刷新
→ 操作 → 结束时可切回
```

### 优点
- bridge 几乎不用改（`@project` 照旧指 ActiveProject）
- 改动集中在 KzMCPServerClient 分发层 + 一个切换工具

### 致命缺点（老隋已明确不要）
- 切换会触发 Kanzi Studio 的未保存改动提示，打断当前编辑
- 全局 ActiveProject 被挪走再挪回，界面焦点/正在编辑的工程会跳
- 并发/多端操作时状态混乱

---

## 关键前置实测（必须先做，不能脑补）

无论 A/B，先连 Studio 验证：

1. `kz_invoke target=@studio method=get_Projects` → 看返回结构、能否枚举出多工程
2. 对**非活跃**工程对象，调 `get_ProjectName` / 无害读操作 → 能否直接访问
3. 对**非活跃**工程对象，能否 `CreateProjectItem`（新建再删，不污染）
4. 能否 `SaveProject(该工程对象)`

> 第 3/4 步决定方案 A 是否成立。若 Kanzi 底层强制 ActiveProject 上下文才能写，
> 则只能方案 B（或 A+B 混合：内部临时切+切回，但用 UnblockStudioModification 尽量减少打扰）。

## ✅ 实现状态更新（2026-08-17 老隋拍板：按方案 A）

老隋确认按**方案 A**（不切 ActiveProject 的最小侵入方案）实现。已落地：

- `KzMCPReflectionBridge.cs`：新增 ProjectSlot 工程池 + GetSolution/RefreshProjects/ListProjects/SelectProject/GetSelectedProjectName/ResolveProjPath；Refresh/ResolveObject/InvokeCore 增加 V12 钩子。
- `KzMCPServerClient.cs`：新增 `kz_list_projects`、`kz_select_project` 工具 + `kz_invoke` target 支持 `@proj:<工程名>[/路径]`。
- 新增 `README_V12.md`（含反编译确认的枚举路径 + 待实测清单）。

**关键反编译纠正（dnfile 2026-08-17）：** `KanziStudio` 没有 `get_Projects`！
多工程枚举在 **`Solution.get_Projects()`**（返回 `IEnumerable<Project>`，签名 `20 00 15 12 49 01 12 85 78`）。
枚举路径：`@studio.get_Solution() → Solution → get_Projects()`。
`KanziStudio` 只有 `get_Project/get_Solution/get_PrimaryProject/get_ActiveProject`。

**待实测（连真实 Studio 后）：** ① get_Projects 可 foreach；② 非激活工程写操作是否被放行（方案 A 下一验证点）；③ 非激活工程 get_WrappedItem 是否可用。
